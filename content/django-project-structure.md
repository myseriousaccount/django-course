# Структура проєкту

`startproject` створює каркас, з якого Django очікує, що проєкт складатиметься. Урок розбирає, що саме з'являється на диску, які файли обов'язкові, і чому папка починає працювати лише після запису в `settings.py`.

## Проєкт і застосунок

**Проєкт** — сайт цілком: налаштування, головна таблиця маршрутів, точки входу для сервера. Він один.

**Застосунок (app)** — функціональна частина проєкту з власними моделями, views і шаблонами. Їх багато: у блог-платформі це `blog`, `accounts`, `comments`; у бібліотеці — `catalog`, `members`, `loans`.

Проєкт нічого не робить сам: уся предметна логіка живе в застосунках, а проєкт лише збирає їх разом і задає спільні налаштування.

## Що створює startproject

```
myshop/
├── manage.py              # точка входу для команд
└── config/                # пакет проєкту (ім'я задала команда startproject)
    ├── __init__.py
    ├── settings.py        # налаштування
    ├── urls.py            # головна таблиця маршрутів
    ├── wsgi.py            # точка входу для синхронного сервера
    └── asgi.py            # точка входу для асинхронного сервера
```

| Файл | Призначення |
|---|---|
| `manage.py` | виконує команди в контексті проєкту: `runserver`, `migrate`, `startapp` |
| `config/__init__.py` | робить папку Python-пакетом |
| `config/settings.py` | `INSTALLED_APPS`, `DATABASES`, `TEMPLATES`, `MIDDLEWARE`, статика, `SECRET_KEY`, `DEBUG` |
| `config/urls.py` | сюди потрапляє кожен запит, звідси розподіляється по застосунках через `include()` |
| `config/wsgi.py`, `config/asgi.py` | використовуються бойовим сервером; у розробці їх не чіпають |

Ці п'ять файлів створюються автоматично й потрібні завжди. Решта — застосунки, шаблони, статика — додається в міру потреби.

> <i class="bi bi-pin-angle"></i> Якщо проєкт назвали так само, як кореневу папку (наприклад, `root`), у дереві буде дві папки `root/`: зовнішня — просто тека на диску, внутрішня — пакет із налаштуваннями. Це очікувано, а не помилка структури.

## Як виглядає проєкт із застосунками

Після кількох `startapp` структура набуває звичного вигляду:

```
shop/
├── manage.py
├── db.sqlite3               # з'являється після migrate (для SQLite)
├── config/                  # пакет проєкту
│   ├── settings.py
│   └── urls.py
├── catalog/                 # застосунок: товари й категорії
├── carts/                   # застосунок: кошик
├── accounts/                # застосунок: користувачі
├── templates/               # спільні шаблони проєкту
└── static/                  # спільні CSS, JS, зображення
```

Шаблони й статика можуть лежати двома способами: спільними папками в корені (як вище) або всередині кожного застосунку (`catalog/templates/catalog/`). Другий варіант робить застосунок самодостатнім і придатним до перенесення в інший проєкт, тому в документації Django його показують як основний.

## Що всередині застосунку

```
blog/
├── __init__.py
├── admin.py          # реєстрація моделей в адмін-панелі
├── apps.py           # конфігурація застосунку
├── models.py         # моделі: Post, Comment
├── views.py          # обробники запитів
├── tests.py          # тести
└── migrations/       # історія змін схеми БД
    └── __init__.py
```

`urls.py` тут немає: його створюють вручну, коли застосунок обслуговує власні маршрути. Так само за потреби додають `forms.py`, `templatetags/`, `templates/`, `static/`.

## Структуру вмикає settings.py

Папка на диску сама по собі нічого не означає. Django дізнається про неї з налаштувань:

```python
# config/settings.py
ROOT_URLCONF = 'config.urls'              # де шукати головну таблицю маршрутів
WSGI_APPLICATION = 'config.wsgi.application'

INSTALLED_APPS = [
    # ... вбудовані django.contrib.* ...
    'blog',                               # застосунки проєкту
    'accounts',
    'comments',
]

TEMPLATES = [{
    'DIRS': [BASE_DIR / 'templates'],     # спільні шаблони проєкту
    'APP_DIRS': True,                     # плюс шаблони всередині застосунків
}]
```

Тому створення папки командою `startapp` — лише половина роботи: доки застосунку немає в `INSTALLED_APPS`, його моделі не потраплять у міграції, шаблони не знайдуться, а адмін-панель залишиться порожньою.

## Чому шаблони кладуть у підпапку з іменем застосунку

Django шукає шаблон за іменем у всіх джерелах підряд і бере перший знайдений. Якщо і `blog`, і `accounts` матимуть `index.html`, вибір виявиться випадковим — переможе той застосунок, що стоїть вище в `INSTALLED_APPS`.

```
blog/templates/blog/post_list.html        # ім'я унікальне: blog/post_list.html
accounts/templates/accounts/login.html    # accounts/login.html
```

Через це у view вказують повний шлях із префіксом застосунку:

```python
# blog/views.py
return render(request, 'blog/post_list.html', {'posts': posts})
```

## Типові помилки / Нюанси

| Що не так | Наслідок і як правильно |
|---|---|
| Застосунок створено, але не доданий в `INSTALLED_APPS` | `makemigrations` каже `No changes detected`, шаблони не знаходяться, в адмінці порожньо. Перше, що перевіряють у нового застосунку |
| Шаблон лежить прямо в `templates/index.html` | При збігу імен Django візьме перший знайдений і покаже чужу сторінку. Завжди підпапка з іменем застосунку |
| Дві однойменні папки проєкту | Нормальна ситуація, якщо ім'я проєкту збіглося з іменем кореневої теки: зовнішня — тека, внутрішня — пакет налаштувань |
| Очікувати `urls.py` після `startapp` | Він не створюється: додається вручну і підключається в головний `urls.py` через `include()` |
| Правити структуру «під себе» | Django шукає файли за конвенцією; довільне розташування вимикає автоматичний пошук шаблонів, статики й міграцій |

## Підсумок

- Проєкт один і містить налаштування, головні маршрути й точки входу; застосунків багато, і саме вони містять предметну логіку.
- `startproject` створює `manage.py` і пакет проєкту з `settings.py`, `urls.py`, `wsgi.py`, `asgi.py`, `__init__.py` — ці файли потрібні завжди.
- `startapp` створює `models.py`, `views.py`, `admin.py`, `apps.py`, `tests.py`, `migrations/`; `urls.py` і `forms.py` додають вручну.
- Папка починає працювати лише після запису в `settings.py`: `INSTALLED_APPS`, `ROOT_URLCONF`, `TEMPLATES`.
- Шаблони розкладають у підпапки з іменем застосунку, інакше однакові імена конфліктують і Django бере перший знайдений файл.
