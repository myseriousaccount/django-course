# Операції з даними: від кнопки до бази

Додати коментар, поставити оцінку, змінити кількість, видалити запис — на вигляд це різні задачі, але всередині вони влаштовані **однаково**. Цей урок збирає розрізнені шматки (маршрут, view, ORM, форма, AJAX) в один повторюваний алгоритм, за яким можна писати будь-яку операцію, навіть ту, якої ти раніше не робила.

## Шість кроків будь-якої операції

Що б користувач не робив, ланцюжок один:

```
1. ТРИГЕР      кнопка або форма на сторінці            (браузер, HTML)
2. АДРЕСА      запит іде на URL                        (urls.py)
3. VIEW        Django викликає функцію-обробник        (views.py)
4. ПЕРЕВІРКИ   хто це? чи можна? чи дані коректні?     (views.py)
5. ДІЯ         створити / змінити / видалити в базі    (ORM)
6. ВІДПОВІДЬ   redirect на сторінку або JsonResponse   (views.py)
```

Кроки 1 і (для AJAX) фінальне оновлення екрана — це браузер. Кроки 2–6 — це сервер. Межа проходить рівно між ними, і плутанина «де фронт, а де бек» зникає, щойно ти навчишся розкладати будь-яку задачу на ці шість пунктів.

| Крок | Де живе код | Що тут вирішується |
|---|---|---|
| Тригер | шаблон (`.html`) | що бачить і натискає користувач |
| Адреса | `urls.py` | який шлях відповідає цій дії |
| View | `views.py` | сценарій обробки |
| Перевірки | `views.py` (+ форма) | права, метод запиту, коректність даних |
| Дія | `models.py` через ORM | що саме змінюється в базі |
| Відповідь | `views.py` | куди потрапляє користувач далі |

> <i class="bi bi-lightbulb"></i> Це як заповнити бланк у поліклініці. Ти віддаєш папірець у віконце (тригер), його несуть у потрібний кабінет (адреса), там сидить конкретний працівник (view), він перевіряє твій паспорт і чи все заповнено (перевірки), вносить запис у журнал (база) і каже, куди йти далі (відповідь). Ти не заходиш у кабінет із журналом сама — і браузер теж не заходить у базу сам.

## Крок 1. Тригер: форма або кнопка

Тригер буває двох видів, і від нього залежить решта.

**Звичайна форма** — браузер сам збирає поля й перезавантажує сторінку:

```html
<form method="post" action="{% url 'comment_add' post.id %}">
    {% csrf_token %}
    <textarea name="text" required></textarea>
    <button type="submit">Надіслати</button>
</form>
```

**Кнопка + JS** — сторінка лишається на місці, запит іде фоном:

```html
{% csrf_token %}
<button class="rate-btn" data-movie-id="{{ movie.id }}" data-score="9">Оцінити 9</button>
```

> <i class="bi bi-info-circle"></i> Зверни увагу, що в обох випадках є `{% csrf_token %}`. Django вимагає токен для **будь-якого** POST, незалежно від того, форма це чи AJAX.

## Крок 2. Адреса: маршрут під дію

Кожна операція — це окремий шлях у `urls.py`. Іменуй їх дієсловами, так читається зрозуміліше:

```python
# blog/urls.py
urlpatterns = [
    path('posts/<int:post_id>/comment/', views.comment_add, name='comment_add'),
    path('comments/<int:comment_id>/delete/', views.comment_delete, name='comment_delete'),
]
```

**Що класти в URL, а що в тіло запиту.** Ідентифікатор об'єкта, над яким працюємо, зручно тримати в адресі (`<int:post_id>`) — тоді він приходить у view як аргумент. Дані, які ввів користувач (текст, кількість, оцінка), ідуть у тілі POST-запиту.

## Крок 3. View: обробник дії

```python
# blog/views.py
def comment_add(request, post_id):
    ...
```

View отримує `request` (усе про запит: метод, дані, користувач) і аргументи з адреси. Далі вона по черзі проходить кроки 4–6.

## Крок 4. Перевірки: три питання перед дією

Перед тим як щось міняти в базі, view відповідає на три питання — **завжди в такому порядку**:

**1) Чи це той метод?** Дії, що змінюють дані, приймають лише POST. Найпростіший спосіб — декоратор:

```python
from django.views.decorators.http import require_POST

@require_POST
def comment_add(request, post_id):
    ...
```

**Навіщо.** Якщо дозволити GET, дію можна буде виконати простим переходом за посиланням — а пошуковий робот або передзавантаження в браузері «клікнуть» його за користувача. Класична історія: сайт, де видалення було звичайним `<a href="/delete/5/">`, і одного дня робот обійшов усі посилання.

**2) Чи має право цей користувач?**

```python
from django.contrib.auth.decorators import login_required

@login_required
@require_POST
def comment_add(request, post_id):
    ...
```

А якщо дія стосується чужого об'єкта — перевіряй власника явно:

```python
comment = get_object_or_404(Comment, pk=comment_id, author=request.user)
# чужий коментар просто не знайдеться → 404, і видалити його не вийде
```

**3) Чи коректні дані?**

```python
text = request.POST.get('text', '').strip()
if not text:
    messages.error(request, 'Коментар не може бути порожнім')
    return redirect('post_detail', post_id=post_id)
```

Для двох-трьох полів вистачає таких перевірок вручну, для складніших — бери форму (`Form` чи `ModelForm`) і `is_valid()`: там валідація вже написана.

> <i class="bi bi-exclamation-triangle"></i> **Ніколи не бери особу користувача з даних запиту.** `user_id` з прихованого поля форми чи з `data` в AJAX підробляється за пів хвилини через DevTools. Єдине надійне джерело — `request.user`, бо його заповнює сам Django на основі підписаної сесійної cookie.

## Крок 5. Дія: чотири операції ORM

| Операція | ORM | Типовий метод |
|---|---|---|
| Створити | `Model.objects.create(...)` | POST |
| Створити, якщо ще немає | `Model.objects.get_or_create(...)` | POST |
| Оновити | `obj.поле = ...` + `obj.save()` | POST |
| Видалити | `obj.delete()` | POST |
| Прочитати | `Model.objects.filter(...)` | GET |

Тут немає нічого специфічного для «операцій» — це той самий ORM з уроку про запити. Важливо лише, що **робота з базою відбувається тільки тут**, у view, і ніде більше.

## Крок 6. Відповідь: redirect чи JSON

Це той момент, який і визначає, чи потрібен тобі AJAX.

**Класика — `redirect`.** Після успішного POST завжди перенаправляй, а не рендери сторінку (патерн Post/Redirect/Get):

```python
messages.success(request, 'Коментар додано')
return redirect('post_detail', post_id=post_id)
```

**AJAX — `JsonResponse`.** Повертаєш рівно ті дані, які потрібні, щоб оновити шматок сторінки:

```python
return JsonResponse({
    'comment_id': comment.id,
    'total': post.comments.count(),
    'message': 'Коментар додано',
})
```

## Та сама дія двома способами

Порівняй два повні варіанти однієї операції — «додати коментар до статті». Різниця лише в кроках 1 і 6.

**Варіант А: звичайна форма**

```python
# blog/views.py
@login_required
@require_POST
def comment_add(request, post_id):
    post = get_object_or_404(Post, pk=post_id)
    text = request.POST.get('text', '').strip()

    if not text:
        messages.error(request, 'Коментар не може бути порожнім')
        return redirect('post_detail', post_id=post.id)

    Comment.objects.create(post=post, author=request.user, text=text)
    messages.success(request, 'Коментар додано')
    return redirect('post_detail', post_id=post.id)
```

```html
<form method="post" action="{% url 'comment_add' post.id %}">
    {% csrf_token %}
    <textarea name="text"></textarea>
    <button>Надіслати</button>
</form>
```

Сторінка перезавантажилась, коментар видно в списку, повідомлення показалось. **JavaScript тут не потрібен взагалі.**

**Варіант Б: AJAX**

```python
# blog/views.py
@require_POST
def comment_add_ajax(request, post_id):
    if not request.user.is_authenticated:
        return JsonResponse({'message': 'Увійдіть, щоб коментувати'}, status=401)

    post = get_object_or_404(Post, pk=post_id)
    text = request.POST.get('text', '').strip()

    if not text:
        return JsonResponse({'message': 'Коментар не може бути порожнім'}, status=400)

    comment = Comment.objects.create(post=post, author=request.user, text=text)

    return JsonResponse({
        'author': comment.author.username,
        'text': comment.text,
        'total': post.comments.count(),
    })
```

```js
$('#comment-form').on('submit', function (e) {
    e.preventDefault();

    $.ajax({
        url: $(this).attr('action'),
        method: 'POST',
        data: $(this).serialize(),          // усі поля разом із csrf-токеном
        success: function (response) {
            $('#comments').append(`<li><b>${response.author}</b>: ${response.text}</li>`);
            $('#comments-count').text(response.total);
            $('#comment-form textarea').val('');     // очистити поле
        },
        error: function (xhr) {
            alert(xhr.responseJSON?.message || 'Не вдалося додати коментар');
        }
    });
});
```

Порівняй уважно: **кроки 2–5 ідентичні**. Маршрут, перевірки, `Comment.objects.create()` — усе те саме. Змінилися тільки тригер (форма сама vs форма + `preventDefault`) і відповідь (`redirect` vs `JsonResponse`), плюс з'явився сьомий крок — оновити сторінку руками в `success`.

> <i class="bi bi-pin-angle"></i> Ось чому питання «нащо AJAX, якщо є форма?» має просту відповідь: **AJAX не робить нічого нового з даними** — він лише позбавляє перезавантаження й натомість вимагає, щоб ти сама оновила потрібні шматки сторінки. Це не «просунутіший спосіб працювати з базою», а інший спосіб доставити відповідь.

## Як обрати: форма чи AJAX

| Ознака | Бери форму | Бери AJAX |
|---|---|---|
| Що має статися після дії | перейти на іншу сторінку або оновити всю поточну | лишитися на місці, змінити дрібницю |
| Скільки всього змінюється | багато (новий список, новий стан сторінки) | один лічильник, кнопка, рядок |
| Скільки коду | менше: Django робить усе сам | більше: плюс JS і оновлення DOM руками |
| Приклади | реєстрація, оформлення замовлення, публікація статті | лайк, оцінка, кошик, «завантажити ще», жива пошук |

**Практичне правило:** починай із форми. Якщо після дії користувач має лишитися рівно там, де був, і мигання сторінки псує враження — переписуй на AJAX. Ніколи не навпаки: AJAX «бо сучасно» додає коду й багів на рівному місці. Детальніше про вибір — в уроці «AJAX: коли застосовувати».

## Чеклист: як написати нову операцію

Коли не знаєш, з чого почати, іди строго по списку:

1. **Сформулюй дію одним реченням**: «залогінений користувач видаляє свій коментар».
2. **Що змінюється в базі?** Який рядок якої моделі створюється, оновлюється чи зникає. Якщо не можеш назвати модель — операція ще не продумана.
3. **Придумай URL** і додай його в `urls.py` з іменем.
4. **Створи view** і одразу постав `@require_POST` та потрібний захист прав.
5. **Дістань дані**: `request.POST.get(...)` для введеного, аргумент URL для id об'єкта, `request.user` для особи.
6. **Дістань об'єкт безпечно**: `get_object_or_404(...)`, за потреби з фільтром власника.
7. **Зроби дію ORM** — один-два рядки.
8. **Поверни відповідь**: `redirect` (+ `messages`) або `JsonResponse` з тими даними, які потрібні фронту.
9. **Під'єднай тригер** у шаблоні: форма з `{% csrf_token %}` або кнопка з `data-`атрибутами і `$.ajax`.
10. **Перевір руками**: спрацювало як залогінений, як гість, з чужим об'єктом, з порожніми даними. Дивись у DevTools → Network: URL, статус, тіло відповіді.

## Спробуй сама: кошик

Тепер повернись до свого магазину — там дві дії, яких ще немає. Не підглядай у готовий код, пройди чеклістом.

**Задача 1: видалити товар із кошика.**
- Що змінюється в базі? Один рядок `CartItem` зникає.
- Питання, які треба вирішити самій: як view дізнається, **який саме** рядок видаляти (id у формі чи в URL?); як не дати видалити чужий рядок (підказка: `get_object_or_404(CartItem, pk=..., user=request.user)`); форма чи AJAX (кошик — сторінка, де перезавантаження цілком нормальне, тож почни з форми).
- Що повернути: `redirect` назад на сторінку кошика.

**Задача 2: змінити кількість товару.**
- Що змінюється: поле `quantity` в наявному рядку `CartItem` — отже, це **оновлення**, а не створення.
- Питання: звідки взяти нове значення (`request.POST.get('quantity')`); що робити, якщо прийшло `0` або від'ємне; чи перераховувати суму на сервері (так — сума завжди рахується на сервері, клієнту не довіряй).
- Тут AJAX доречніший: користувач крутить кількість і одразу бачить нову суму, не перезавантажуючи кошик.

**Задача 3 (бонус):** зроби так, щоб повторне «Додати в кошик» не створювало другий рядок, а збільшувало `quantity` на одиницю. Підказка — `get_or_create()` з уроку про ORM-запити.

## Типові помилки / Нюанси

| Що не так | Наслідок і як правильно |
|---|---|
| Дія, що змінює дані, через GET-посилання | `<a href="/comments/5/delete/">` спрацює від переходу за посиланням: пошуковий робот, передзавантаження браузера, чуже посилання в чаті. Тільки POST і тільки з CSRF-токеном |
| `render` замість `redirect` після POST | Оновлення сторінки (F5) надішле форму вдруге й створить дублікат. Після успішного POST — завжди `redirect` |
| Довіра до прихованих полів і `data` | `<input type="hidden" name="price">` чи `user_id` підміняються за пів хвилини в DevTools. Ціну бери з бази за id, користувача — з `request.user` |
| Логіка на клієнті | Сума, дозвіл на видалення, залишок на складі, обчислені в JavaScript, нічого не гарантують. Рішення ухвалює view, браузер лише показує результат |
| В AJAX оброблено лише `success` | При 403 або 500 користувач бачить, що «нічого не сталося». Гілка `error` обов'язкова |
| Дублікати від подвійного кліку | Захист із двох боків: вимкнути кнопку на час запиту та `unique_together` або `get_or_create()` у базі |

## Підсумок

- Будь-яка операція з даними — це шість кроків: **тригер → адреса → view → перевірки → дія ORM → відповідь**. Тригер і фінальне оновлення екрана в браузері, решта на сервері.
- Форма й AJAX відрізняються **лише кроками 1 і 6**; маршрут, перевірки й робота з базою в них однакові.
- AJAX не дає нового доступу до даних — він лише прибирає перезавантаження, а оновлення сторінки перекладає на тебе.
- Перед дією view відповідає на три питання: правильний **метод** (`@require_POST`), достатні **права** (`@login_required`, фільтр за власником), коректні **дані** (перевірка або форма).
- Особу користувача бери **тільки з `request.user`**, ціни й суми рахуй **на сервері** — усе, що прийшло з браузера, підробляється.
- Після успішного POST — `redirect` + `messages`, а не `render`.
- Не знаєш, з чого почати нову дію: пройдись чеклістом із десяти пунктів, починаючи з питання «який рядок якої моделі змінюється».
