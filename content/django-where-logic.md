# Де живе логіка

Підрахунки, правила й перевірки можна писати прямо у view — і це нормальна відправна точка. Питання «куди це винести» виникає пізніше, коли той самий код знадобився вдруге. Урок — оглядовий: за якою ознакою обирають місце й куди дивитися далі.

## Правило вибору

| Ситуація | Де писати | Детально |
|---|---|---|
| код потрібен в одній view і більше ніде | лишається у view | — |
| обчислення стосується **одного** об'єкта | метод моделі | урок «Методи моделі» |
| обчислення стосується **набору** об'єктів | метод менеджера | урок «Менеджери й власні вибірки» |
| дія зачіпає **кілька** моделей одразу | окремий модуль із логікою | нижче в цьому уроці |

Порядок саме такий: спершу пиши там, де використовується, виноси тоді, коли з'явився другий виклик. Виносити наперед — ускладнення без причини.

## Що дає винесення

```python
# ❌ shop/views.py — правило знижки живе всередині обробника запиту
def checkout(request, order_id):
    order = Order.objects.get(id=order_id)

    total = sum(i.price * i.quantity for i in order.items.all())
    if total > 1000:
        total *= 0.9

    order.total = total
    order.status = 'paid'
    order.save()

    return render(request, 'orders/done.html', {'order': order})
```

```python
# ✅ shop/views.py — view приймає запит і делегує
def checkout(request, order_id):
    order = get_object_or_404(Order, pk=order_id, user=request.user)
    order.mark_paid()
    return render(request, 'orders/done.html', {'order': order})
```

Різниця не в кількості рядків, а в тому, що правило знижки тепер доступне поза HTTP-запитом: його викликає і команда `manage.py`, і дія в адмінці, і тест — без імітації запиту. Поки воно лежить у view, кожне з цих місць змушене копіювати підрахунок.

## Логіка кількох моделей

Коли дія зачіпає одразу кілька моделей і не належить жодній із них, її виносять в окремий модуль. Усталена назва — `services.py`, але це конвенція, а не вимога фреймворку.

```python
# shop/services.py
from django.db import transaction


@transaction.atomic
def place_order(user, cart_items):
    order = Order.objects.create(user=user)

    for item in cart_items:
        OrderItem.objects.create(
            order=order,
            product=item.product,
            quantity=item.quantity,
            price_at_purchase=item.product.price,
        )
        item.product.count -= item.quantity
        item.product.save(update_fields=['count'])

    cart_items.delete()
    return order
```

```python
# shop/views.py
@require_POST
def checkout(request):
    items = CartItem.objects.for_user(request.user)
    order = place_order(request.user, items)
    return redirect('order_detail', pk=order.pk)
```

Оформлення замовлення створює замовлення, списує залишки й чистить кошик — тобто стосується трьох моделей. Тому це не метод жодної з них.

`@transaction.atomic` означає, що всі зміни застосуються разом або жодна: якщо на середині списання станеться помилка, у базі не лишиться замовлення без позицій і списаних залишків без замовлення.

## Що з чим не плутати

| Шар | Відповідає за | Не має робити |
|---|---|---|
| Шаблон | виведення готових даних | обчислення, запити до бази |
| View | прийняти запит, перевірити права, віддати відповідь | правила предметної області |
| Модель і менеджер | дані та операції над ними | знати про HTTP, `request`, шаблони |
| Модуль із логікою | сценарії між кількома моделями | імпортувати views |

## Типові помилки / Нюанси

| Що не так | Наслідок і як правильно |
|---|---|
| Виносити наперед, «щоб було правильно» | Три шари заради одного виклику; виносять, коли з'явився другий |
| Правило залишилось у view, хоч потрібне в кількох місцях | Копії розходяться, і зміна правила ламає частину сторінок |
| Метод моделі працює з кількома моделями | Модель починає знати про чужі таблиці; це сценарій для окремого модуля |
| Модуль із логікою приймає `request` | Логіка прив'язується до HTTP і стає непридатною для команд і тестів |
| Кілька залежних записів без `transaction.atomic` | Помилка посеред операції лишає базу в половинному стані |
| Обчислення в шаблоні | Розмітка ухвалює рішення, які неможливо ні протестувати, ні перевикористати |

## Підсумок

- Код у view — нормальна відправна точка; виносять тоді, коли він знадобився вдруге.
- Один об'єкт — метод моделі, набір об'єктів — метод менеджера, кілька моделей — окремий модуль.
- Винесення дає не красу, а доступність логіки поза запитом: команди, адмінка, тести.
- Сценарії з кількох записів обгортають у `transaction.atomic`, щоб база не лишилась у половинному стані.
- Межі шарів: шаблон лише виводить, view приймає запит і перевіряє права, модель зберігає правила про дані, модуль із логікою поєднує моделі й нічого не знає про HTTP.
