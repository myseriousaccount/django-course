# Застосунки (apps)

Застосунок — самодостатня частина проєкту, що закриває одну функціональну область: каталог товарів, статті, облік читачів. Проєкт складається із застосунків, і саме в них лежить уся предметна логіка.

## Як ділити проєкт

Межа проходить за областю даних і задач, а не за кількістю сторінок. Три сторінки головного розділу (`index`, `about`, `contacts`) — це один застосунок, бо вони пов'язані змістом і не мають власних моделей.

| Проєкт | Застосунки | Область кожного |
|---|---|---|
| Магазин | `catalog`, `carts`, `orders`, `accounts` | товари, кошик, замовлення, користувачі |
| Блог | `blog`, `comments`, `accounts` | статті, коментарі, автори |
| Бібліотека | `catalog`, `loans`, `members` | книги, видача, читачі |

Робочий критерій: якщо частину можна описати одним іменником і в неї є власні моделі — це окремий застосунок. Якщо для неї не знаходиться жодної моделі й вона лише показує сторінки — найчастіше це частина наявного застосунку.

Другий критерій — перевикористання. Застосунок `accounts` із реєстрацією й входом однаково потрібен магазину, блогу й бібліотеці; якщо він не переплетений із товарами, його можна перенести в інший проєкт майже без змін.

> <i class="bi bi-info-circle"></i> Якщо порівнювати з Flask, застосунок відповідає blueprint. Різниця в тому, що тут це не домовленість, а частина фреймворку: Django сам шукає в застосунку моделі, міграції, шаблони, статику й теги.

## Створення

```bash
python manage.py startapp blog
```

```
blog/
├── __init__.py
├── admin.py
├── apps.py
├── models.py
├── tests.py
├── views.py
└── migrations/
    └── __init__.py
```

`urls.py` не створюється — його додають, коли застосунок обслуговує власні маршрути. Призначення кожного файлу розібране в уроці «Файли застосунку».

Команда приймає одне ім'я. Кілька застосунків створюють послідовно або циклом:

```bash
for app in catalog carts orders accounts; do
    python manage.py startapp $app
done
```

Імена дають у нижньому регістрі, зазвичай у множині за предметом (`orders`, `members`) або одним словом за областю (`catalog`, `blog`). Ім'я стає префіксом в імпортах і в шляхах шаблонів, тому змінювати його пізніше дорого.

## Реєстрація

Створена папка ще нічого не означає. Застосунок вмикається записом у налаштуваннях:

```python
# config/settings.py
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    'blog',
    'comments',
    'accounts',
]
```

Без цього рядка Django не побачить моделі застосунку (їх не буде в міграціях), не знайде його шаблони й статику, не покаже його в адмін-панелі.

Рядок можна вказати двома способами: коротким іменем пакета (`'blog'`) або повним шляхом до класу конфігурації (`'blog.apps.BlogConfig'`). Перший варіант Django сам розгортає у другий, тому в звичайному проєкті достатньо короткого. Повний шлях потрібен, коли в застосунку кілька класів конфігурації або коли треба гарантовано вибрати конкретний.

## Проєкт і застосунки разом

```python
# config/urls.py
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('home.urls')),
    path('blog/', include('blog.urls')),
    path('accounts/', include('accounts.urls')),
]
```

Проєкт знає про всі застосунки й розподіляє між ними запити; кожен застосунок відповідає за свій префікс адрес і свої дані. Змінюючи предметну область, ти працюєш в одній папці, а не по всьому проєкту.

## Типові помилки / Нюанси

| Що не так | Наслідок і як правильно |
|---|---|
| Застосунок не доданий в `INSTALLED_APPS` | `makemigrations` відповідає `No changes detected`, шаблони не знаходяться, адмінка порожня. Найчастіша причина «нічого не працює» в новому застосунку |
| Один застосунок на весь проєкт | Моделі, views і шаблони різних областей змішуються; змінити одну частину, не зачепивши інші, стає неможливо |
| Застосунок на кожну сторінку | Десяток майже порожніх папок і маршрути, розкидані по всьому проєкту. Дроби за областю даних, а не за сторінками |
| Перейменування застосунку після старту | Ламаються імпорти, шляхи шаблонів і посилання в міграціях. Ім'я обирають одразу |
| Прямі імпорти між застосунками в обидва боки | Циклічний імпорт і падіння при старті. Зв'язок описують рядком: `ForeignKey('catalog.Product', ...)` |

## Підсумок

- Застосунок закриває одну функціональну область; критерій поділу — власні моделі й можливість описати частину одним іменником.
- `python manage.py startapp <ім'я>` створює каркас; `urls.py` додають вручну.
- Застосунок працює лише після запису в `INSTALLED_APPS` — коротким іменем або повним шляхом до `AppConfig`.
- Ім'я застосунку стає префіксом імпортів і шаблонів, тому його не змінюють згодом.
- Проєкт розподіляє запити між застосунками через `include()`; кожен застосунок лишається самодостатнім і придатним до перенесення.
