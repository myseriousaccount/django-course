# Що таке Django

Django — вебфреймворк мовою Python для сайтів, що працюють з базою даних. Він побудований за принципом «batteries included»: ORM, маршрутизація, шаблони, форми, автентифікація й адміністративна панель входять у поставку, а не добираються сторонніми пакетами.

## Full-stack проти мікрофреймворку

Flask дає мінімальне ядро й лишає вибір бібліотек за тобою. Django дає готовий набір і очікує, що проєкт дотримуватиметься його конвенцій.

| | Flask | Django |
|---|---|---|
| Робота з БД | окремо, зазвичай Flask-SQLAlchemy | вбудований ORM |
| Міграції | окремо, Flask-Migrate | вбудовані (`makemigrations`, `migrate`) |
| Автентифікація | окремо, Flask-Login | `django.contrib.auth` |
| Форми й валідація | окремо, WTForms | `django.forms` |
| Адмін-панель | пишеш сам | готова, на `/admin` |
| Маршрути | декоратори `@app.route` | окремі файли `urls.py` |
| Структура проєкту | довільна | задана конвенціями |

Наслідок для роботи: у Flask рішення «де лежить модель» і «як організувати папки» ухвалюєш ти, у Django ці рішення вже ухвалені. Це звужує свободу, але прибирає клас питань «а як тут правильно» і робить чужий проєкт передбачуваним.

## MTV: три шари

Django реалізує той самий поділ відповідальності, що й MVC, але називає шари інакше.

| Шар | Що описує | Файл |
|---|---|---|
| **Model** | структуру даних і таблиці БД | `blog/models.py` |
| **Template** | HTML, який бачить користувач | `blog/templates/blog/post_list.html` |
| **View** | обробку запиту: взяти дані, обрати шаблон, повернути відповідь | `blog/views.py` |

> <i class="bi bi-exclamation-triangle"></i> Django-**View** відповідає тому, що в MVC називають контролером, а MVC-view тут називається **Template**. Це головна плутанина при переході з іншого фреймворку.

Шлях запиту на сторінку списку статей:

```
GET /blog/  →  root/urls.py  →  blog/urls.py  →  blog/views.py: post_list()
                                                       ↓
                                        blog/models.py: Post.objects.all()
                                                       ↓
                              blog/templates/blog/post_list.html  →  HTML-відповідь
```

Той самий шлях у коді:

```python
# blog/models.py
class Post(models.Model):
    title = models.CharField(max_length=200)
    body = models.TextField()
    published_at = models.DateTimeField(auto_now_add=True)
```

```python
# blog/views.py
from django.shortcuts import render
from .models import Post


def post_list(request):
    posts = Post.objects.all()
    return render(request, 'blog/post_list.html', {'posts': posts})
```

```html
{# blog/templates/blog/post_list.html #}
{% for post in posts %}
  <article><h2>{{ post.title }}</h2></article>
{% endfor %}
```

Модель не знає про HTML, шаблон не звертається до бази, view з'єднує їх. Порушення цього поділу — найчастіша причина, чому проєкт стає важко змінювати.

## Що входить у поставку

Вбудовані застосунки лежать у пакеті `django.contrib` і вмикаються через `INSTALLED_APPS`. Шість із них `startproject` додає одразу:

```python
# root/settings.py
INSTALLED_APPS = [
    'django.contrib.admin',         # адмін-панель на /admin
    'django.contrib.auth',          # користувачі, групи, права, паролі
    'django.contrib.contenttypes',  # облік типів моделей (потрібен auth і правам)
    'django.contrib.sessions',      # серверні сесії
    'django.contrib.messages',      # одноразові повідомлення
    'django.contrib.staticfiles',   # роздача CSS, JS, зображень
    'blog',                         # власні застосунки проєкту
    'accounts',
]
```

Решта підключається за потреби:

| Застосунок | Що дає |
|---|---|
| `django.contrib.humanize` | форматування чисел і дат для людей («2 хвилини тому») |
| `django.contrib.sitemaps` | генерація `sitemap.xml` |
| `django.contrib.syndication` | RSS- і Atom-стрічки |
| `django.contrib.gis` | геодані: координати, карти, просторові запити |

Практична різниця: типовий сайт із користувачами на Flask збирається з Flask, Flask-SQLAlchemy, Flask-Migrate, Flask-Login, WTForms і власноруч написаної адмінки. У Django це одна залежність і кілька рядків налаштувань.

## Коли Django, а коли Flask

- **Django** — коли в проєкті є база даних, користувачі, форми й потрібна панель керування вмістом: блог, магазин, каталог бібліотеки, довідник фільмів, внутрішня система обліку.
- **Flask** — коли потрібне мале й нестандартне: сервіс на кілька ендпоінтів, обгортка над API, бот, прототип із власною архітектурою.

Орієнтир: якщо в проєкті будуть пов'язані між собою таблиці (пости й коментарі, товари й замовлення) і хтось адмініструватиме вміст через інтерфейс — виграш від Django максимальний.

## Типові помилки / Нюанси

| Що не так | Наслідок і як правильно |
|---|---|
| Шукати в Django «контролер» | Окремого шару контролерів немає: його роль виконує view, а MVC-view тут називається шаблоном |
| Логіка роботи з даними в шаблоні | Шаблон має лише виводити готове; запити до бази й обчислення лишаються у view або моделі, інакше сторінку неможливо ні протестувати, ні перевикористати |
| «Django виправданий лише для великих проєктів» | Для малого сайту з базою він теж доречний — просто частина вбудованих застосунків лишиться невикористаною |
| Плутати проєкт і застосунок | Проєкт містить налаштування й головні маршрути, застосунок закриває одну функціональну область; детально — в уроці «Застосунки (apps)» |

## Підсумок

- Django — full-stack фреймворк: ORM, міграції, автентифікація, форми, сесії та адмін-панель входять у поставку.
- Архітектура — **MTV**: модель описує дані, шаблон — розмітку, view обробляє запит і з'єднує їх. View у Django = контролер у MVC.
- Вбудовані застосунки лежать у `django.contrib`; шість увімкнено за замовчуванням, решта додається в `INSTALLED_APPS` за потреби.
- На відміну від Flask, структура проєкту задана конвенціями — менше рішень на кожному кроці й передбачуваний вигляд чужого коду.
- Django обирають під проєкти з базою, користувачами й адмініструванням вмісту; Flask — під малі та нестандартні задачі.
