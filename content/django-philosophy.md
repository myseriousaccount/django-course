# Принципи Django

Структура Django виглядає як набір довільних правил, поки не видно принципів, з яких вона виведена. Їх чотири, і кожен має пряме відображення в коді, який ти пишеш щодня.

## DRY: одна одиниця знання — одне місце

Опис сутності існує в проєкті один раз, усе похідне фреймворк виводить із нього сам.

```python
# catalog/models.py
class Product(models.Model):
    name = models.CharField(max_length=200)
    price = models.DecimalField(max_digits=10, decimal_places=2)
```

З цього опису Django отримує структуру таблиці (через міграції), поля форми в `ModelForm`, інтерфейс редагування в адмін-панелі та правила валідації. Опис товару не дублюється в чотирьох місцях — тому зміна `max_length` в одному рядку розходиться по всьому проєкту.

Практичний наслідок: якщо ти ловиш себе на тому, що те саме правило записане двічі (у моделі й у формі, у формі й у JavaScript), це майже завжди означає, що є вбудований механізм, який ти обходиш.

## Конвенція над конфігурацією

Фреймворк діє за усталеними правилами за замовчуванням, тож налаштовувати доводиться лише відхилення від них. Django сам знайде:

| Що | Де очікує знайти |
|---|---|
| моделі застосунку | `app/models.py` |
| маршрути застосунку | `app/urls.py`, підключені в `root/urls.py` |
| шаблони | `app/templates/app/` |
| статику | `app/static/app/` |
| теги шаблонів | `app/templatetags/` |
| міграції | `app/migrations/` |

> <i class="bi bi-pin-angle"></i> «Над», а не «замість»: конфігурація нікуди не зникає, її можна змінити в `settings.py`. Конвенція працює як дефолт, а не як заборона.

Зворотний бік — конвенції треба знати. Файл, названий інакше, або шаблон у неправильній папці просто не буде знайдений, причому без явної помилки: Django повідомить, що шаблону не існує.

## Явне краще за неявне

Залежності передаються відкрито, а не беруться з прихованого глобального контексту:

```python
# blog/views.py
def post_list(request):        # об'єкт запиту приходить аргументом
    ...
```

У Flask `request` — глобальний проксі-об'єкт, доступний будь-де після імпорту. Django передає його параметром, тому за сигнатурою функції одразу видно, з чим вона працює. Той самий принцип видно в `ForeignKey(..., on_delete=...)`: Django не обирає поведінку за тебе, а вимагає вказати її явно.

Наслідок: менше прихованого стану — простіше тестувати. Щоб перевірити view, достатньо передати їй підготовлений `request`.

## Слабка зв'язність

Проєкт ділиться на застосунки, а всередині — на шари, які не знають деталей одне одного: модель не формує HTML, шаблон не звертається до бази, view з'єднує їх.

```python
# ✅ шари розділені
def post_list(request):
    posts = Post.objects.filter(is_published=True)          # дані
    return render(request, 'blog/post_list.html', {'posts': posts})   # відображення
```

Наслідок: шаблон можна переписати, не чіпаючи логіку; модель — перенести в інший проєкт разом із застосунком. Порушення зв'язності (HTML, зібраний рядками у view, або SQL у шаблоні) робить обидві частини незамінними.

## Девіз

Неофіційний девіз — **«The web framework for perfectionists with deadlines»**. Це не гасло, а опис компромісу: фреймворк дає готові перевірені рішення, тому швидкість не купується ціною якості. Практично це означає, що на типову задачу (автентифікація, пагінація, адмінка) у Django є штатний спосіб, і власна реалізація майже завжди програє йому в надійності.

## Словник понять

Терміни, які зустрічатимуться в наступних уроках:

| Поняття | Що це | Аналог у Flask |
|---|---|---|
| **Проєкт** | сайт цілком: налаштування, головний `urls.py` | застосунок Flask |
| **App** | модуль під одну функціональну область | blueprint |
| **Model** | клас, що описує таблицю БД | модель SQLAlchemy |
| **ORM** | доступ до бази через Python-об'єкти | Flask-SQLAlchemy |
| **Migration** | версійована зміна структури БД | Flask-Migrate |
| **View** | функція або клас, що обробляє запит | view-функція |
| **Template** | HTML-шаблон із підстановками | шаблон Jinja2 |
| **URLconf** | таблиця маршрутів у `urls.py` | `@app.route` |
| **Middleware** | обробник навколо кожного запиту | `before_request` / `after_request` |
| **Settings** | конфігурація проєкту | `app.config` |

## Типові помилки / Нюанси

| Що не так | Наслідок і як правильно |
|---|---|
| Власна структура папок замість конвенцій | Автоматичний пошук шаблонів, статики й міграцій не спрацює, причому мовчки: Django просто повідомить, що шаблону не існує. Тримайся очікуваних шляхів |
| Те саме правило записане двічі | `max_length` у моделі, ще раз у формі, ще раз у JavaScript розходяться при першій же зміні. Джерело — модель, решта виводиться з неї |
| Читати принципи як заборони | Django дозволяє і сирий SQL, і сторонній шаблонізатор. Відхилення можливе, але має бути свідомим рішенням із причиною, а не випадковістю |

## Підсумок

- **DRY** — сутність описана один раз у моделі; таблиця, форма, адмінка й валідація виводяться з неї.
- **Конвенція над конфігурацією** — Django сам знаходить моделі, шаблони, статику й міграції за очікуваними шляхами; налаштовуються лише відхилення.
- **Явність** — `request` передається аргументом, `on_delete` вимагає рішення; прихованого глобального стану немає.
- **Слабка зв'язність** — застосунки й шари незалежні: модель не формує HTML, шаблон не ходить у базу.
- Девіз «для перфекціоністів із дедлайнами» на практиці означає: на типову задачу є штатний механізм, і він майже завжди надійніший за власну реалізацію.
