# Перший проєкт

Послідовність команд, якими Django-проєкт піднімають з нуля: ізольоване середовище, встановлення пакета, генерація каркаса, перший запуск. Кожен крок пояснено разом із тим, що саме він створює на диску.

## 1. Віртуальне середовище

**venv** — ізольований набір Python-пакетів для одного проєкту. Без нього залежності потрапляють у системний Python і конфліктують між проєктами: один потребує Django 5, інший Django 6.

```bash
python3 -m venv .venv          # створити середовище в папці .venv
source .venv/bin/activate      # активувати (macOS, Linux)
.venv\Scripts\Activate.ps1     # активувати (Windows PowerShell)
```

У команді `python3 -m venv .venv` перша частина запускає вбудований модуль `venv`, друга — задає ім'я папки. Конвенція — `.venv` або `venv`.

Після активації в рядку терміналу з'являється префікс `(.venv)`: усі наступні `pip install` ідуть у це середовище. Вихід — команда `deactivate`.

> <i class="bi bi-info-circle"></i> Папку середовища не версіонують: вона важить сотні мегабайтів і залежить від операційної системи. У `.gitignore` додають `.venv/`, а відтворюваність забезпечує `requirements.txt` із кроку 6.

## 2. Встановлення Django

```bash
pip install django                # остання стабільна версія
pip install "django==6.0.*"       # фіксована серія версій
python -m django --version        # перевірка
```

Для робочого проєкту версію фіксують: без цього наступне встановлення на іншій машині може підтягнути новішу мажорну версію зі зміненою поведінкою.

## 3. Створення проєкту

```bash
django-admin startproject config .
```

- `django-admin` — утиліта, доступна після встановлення пакета; `manage.py` ще не існує, тому команда саме така.
- `config` — ім'я пакета з налаштуваннями: створяться `config/settings.py`, `config/urls.py`, `config/wsgi.py`, `config/asgi.py`. Ім'я довільне, поширені варіанти — `config`, `core`, `root`.
- `.` — створити в поточній папці.

> <i class="bi bi-exclamation-triangle"></i> Без крапки Django створить зайвий рівень вкладеності: `config/config/settings.py` замість `config/settings.py`. Це не помилка, але структура стає незручною, і шляхи в імпортах виглядають інакше, ніж у прикладах документації.

Результат на диску:

```
manage.py            # точка входу для всіх наступних команд
config/
├── __init__.py
├── settings.py      # налаштування проєкту
├── urls.py          # головна таблиця маршрутів
├── wsgi.py          # точка входу для синхронного сервера
└── asgi.py          # точка входу для асинхронного сервера
```

## 4. Початкові міграції

```bash
python manage.py migrate
```

Вбудовані застосунки (`auth`, `sessions`, `admin`, `contenttypes`) мають власні моделі, тож їм потрібні таблиці. Ця команда їх створює і разом із ними — файл бази `db.sqlite3`, якщо в налаштуваннях лишився SQLite за замовчуванням.

Без цього кроку сервер запуститься, але будь-яка сторінка, що звертається до сесій чи користувачів, дасть помилку «no such table».

## 5. Запуск сервера розробки

```bash
python manage.py runserver               # 127.0.0.1:8000
python manage.py runserver 8080          # інший порт
python manage.py runserver 0.0.0.0:8000  # доступ з інших пристроїв мережі
```

`runserver` автоматично перезавантажується при зміні файлів і призначений виключно для розробки: він однопотоковий і не роздає статику ефективно. Для продакшну використовують Gunicorn або uWSGI (WSGI) чи Uvicorn (ASGI) — про це в уроці «Деплой».

## 6. Фіксація залежностей

```bash
pip freeze > requirements.txt      # зберегти поточні версії
pip install -r requirements.txt    # відтворити середовище
```

`requirements.txt` додають у git, папку середовища — ні.

> <i class="bi bi-info-circle"></i> `pip freeze` записує **всі** встановлені пакети, зокрема залежності залежностей. Для невеликого проєкту цього достатньо; у командній роботі частіше тримають окремий файл із прямими залежностями (або переходять на `pyproject.toml` чи `poetry`), щоб було видно, що встановлено свідомо, а що потрапило транзитивно.

## Уся послідовність

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install django
django-admin startproject config .
python manage.py migrate
python manage.py runserver
```

Наступний крок — створення застосунку командою `python manage.py startapp <ім'я>`. Він винесений в окремий урок, бо спершу треба розібратися, за яким принципом проєкт ділять на застосунки.

## Типові помилки / Нюанси

| Симптом або дія | Причина і що робити |
|---|---|
| `django-admin: command not found` | Середовище не активоване або пакет не встановлено. Ознака активації — префікс `(.venv)` у рядку терміналу |
| `That port is already in use` | Попередній `runserver` не зупинено: запусти на іншому порту або зупини процес, що займає 8000 |
| `no such table: django_session` | Не виконано `migrate` після створення проєкту |
| `pip install django` без активованого venv | Пакет стане глобальним; проєкт запрацює, але версії конфліктуватимуть з іншими проєктами на цій машині |
| Забута крапка в `startproject` | З'явиться зайвий рівень вкладеності `config/config/`; простіше видалити папку й повторити команду |
| `django-admin` замість `manage.py` | `django-admin` потрібен лише для `startproject`. Решта команд — через `python manage.py`, бо він вказує Django, де шукати налаштування |

## Підсумок

- `python3 -m venv .venv` + `source .venv/bin/activate` — ізоляція залежностей; папку середовища не версіонують.
- Версію Django для робочого проєкту фіксують: `pip install "django==6.0.*"`.
- `django-admin startproject config .` — крапка означає «в поточній папці»; без неї з'являється зайвий рівень вкладеності.
- `migrate` створює таблиці вбудованих застосунків і файл бази; без нього сторінки з сесіями чи користувачами падають.
- `runserver` — сервер лише для розробки; продакшн обслуговують Gunicorn, uWSGI або Uvicorn.
- `pip freeze > requirements.txt` фіксує версії, `pip install -r requirements.txt` відтворює середовище на іншій машині.
